# 人物分析的等待時間花在哪裡

## ELI5：工具送到家，在家裡算

把網站想成一箱練舞工具。若你開的是 Cloudflare 預覽站，它把網頁、模型與執行工具送到瀏覽器；真正翻影片、找人與移動小相框的是你自己的電腦或手機。在 4174 本機預覽時，工具也由本機主機提供。影片不用送到 Cloudflare 分析。網頁的 Web Worker 像旁邊桌的助手，仍在你的裝置上，和雲端的 Cloudflare Worker 是兩回事。

現在是每秒影片挑八張照片，一張張找出你框的人。含頭尾，10／30／60 秒會看 81／241／481 張；老師與自己的影片各分析一次，就各做一份工作。每輪都重新叫助手、打開模型，再開始看照片；同一段重跑，不代表模型一直留著。

像替每一站蓋時間章：載入影片、移到畫面、擷取圖片、啟動模型、辨識人物各記自己的耗時。#176 原輪只加時間章；後續 #192 用同模型 SIMD 做對照，仍不重用 Worker、降低 8 Hz、放寬跟隨門檻或改匯出。

主線現在找完人還會製作可下載的單側影片。這就像先決定相框怎麼移動，再把移動結果錄成一支影片；兩段都要等，所以碼表分開顯示「分析」「單側製片」和整體等待，製片失敗或取消也保留上次結果。

原版合成片基準的碼表顯示，約 86% 時間在「看照片找人」，約 14% 在「翻到要看的畫面」，重新開模型約 0.18%。它量的是 `5eda868` 上的分析，早於主線 `a3a9859` 的狹框補邊與單側製片整合，不能當作目前整套流程的比例。所以 SIMD 是下一個待驗證實驗，還不是已加速成果，也不能當作你每支舞蹈影片都一樣快。

## 怎麼看自己的數字

選片區展開「人物分析耗時（僅本機數字）」，再照原流程框選。完成、取消或失敗後會顯示最近一輪數字；按「另存耗時報告 JSON」可保存本頁最近十次有開啟紀錄的分析。取消／失敗是部分數據，不當作成功或重跑比較。關閉「記錄這次分析耗時」可作計時開關對照，原分析照常進行，舊報告保留。

同一分頁、同一已載入來源、同側、同片段與同選框的成功輪會列出與上次差幾毫秒。這只表示再次分析相同輸入，每輪仍建立新 Worker／模型，不能叫作「模型已暖機」。換片、改片段／選框、換側或重開頁都不冒充同條件。

報告只有彙總數字、完成狀態與老師／自己角色；不包含影片、影格、檔名、來源 URL、選框座標、絕對時間或硬體指紋。不寫 IndexedDB、不上傳、不逐格印 console；只有使用者點下載才另存。比對來源的有界私有鍵只留記憶體，不雜湊整支私人影片，也不寫進 JSON。

## 技術流程與量測邊界

`follow-ui.js` 建立獨立靜音影片元素，先 load／定位至比較片段起點。確認後，每 0.125 秒來源時間依序 await seek → createImageBitmap → 將原影格轉移至本機 Worker → 等待偵測框；沿既有身分匹配、短暫失聯與平滑計算裁切路徑。後續預覽與 VS 使用同一路徑和原鏡像／時間／音訊規則，沒有新的播放時鐘。8 Hz 是影片時間的取樣密度，實際每秒能處理幾張另由碼表計算，不是強迫分析用原速播放。

`person-worker.js` 沿用固定 EfficientDet-Lite0 int8、IMAGE 模式及 CPU delegate。#176 原版使用非 SIMD，#192 候選依能力選擇 SIMD／相容 WASM，詳見[本輪設計與證據](evidence/issue-192-follow-simd.md)。首次訊息執行 importScripts／createFromOptions，後續每張仍呼叫完整 detector.detect；保留主線狹框的等比補邊與座標還原，補邊準備屬 Worker 等待內其餘工作，沒有混進 detect 呼叫。分析結束即終止模型 Worker，再沿主線製作單側結果；取消仍保留既有成品。快取命中可省網路傳輸，不能直接視為模型物件已初始化。Cloudflare 若作為靜態資源供應端，不參與這條本機影片解碼與推論路徑；基準使用自有 loopback 主機。

以下依原 API 邊界加時鐘，數字隨既有 Worker 回覆返回，沒有新增握手、併發推論、影片上傳或演算法調整。原追蹤與匯出契約仍引用 [RECORD_COMPARE](RECORD_COMPARE.md) 與 [人物跟隨設計](../TECHNICAL.md#165-雙側人物跟隨裁切)。

| 欄位 | 從哪裡量到哪裡 |
| --- | --- |
| 載入／第一次定位 | 按框選後的獨立播放器 load 與接著 seek 到片段起點；在確認前完成，不含人工框選時間。load 本身的內部定位仍屬 load。 |
| Worker 建構 | new Worker 呼叫返回；不是模型已可推論。 |
| Worker 啟動 | 建構前到 Worker 腳本首段執行，以 timeOrigin 對齊；可能與主執行緒定位／擷取重疊。時鐘不一致則留空。 |
| 程式載入／模型初始化 | Worker 的 importScripts 與 createFromOptions 各自包住量測。初始化包含資源讀取／SW 完整性驗證、WASM 與模型建立，不能全當 CPU 推論時間。 |
| 逐次定位 | 原本每次 await seek() 的等待，包含同位置立即完成的首格。不是瀏覽器內部純解碼 CPU 時間。 |
| 擷取影格 | 原 createImageBitmap 的呼叫至完成，不另留影格副本。 |
| 模型推論 | 每次原 detector.detect 的完整同步呼叫，包含套件內部的前／後處理，不能當作純神經網路算子時間；與初始化 API 分開。失敗輪如有回覆亦保留已取得數字。 |
| Worker 等待 | 送出原偵測訊息至收到回覆／取消／錯誤；包含初始化、推論與 IPC，不能再與上述數字相加。 |
| 確認後總分析 | 確認處理開始到路徑平滑與 Worker 釋放，進入製片前停表；未進製片即取消／失敗則記到收尾。處理速度與相同輸入比較只用這段。原 schema 1 基準還包含當時的畫面更新，沒有單側製片。 |
| 單側製片 | 原 makeResult 呼叫至成功／取消／失敗，包含既有編碼、驗證等工作；未進入則為 null。不是純編碼 CPU 時間，也不改錄製速度或流程。 |
| 確認後總等待 | 確認處理開始到原成功交換／錯誤收尾；含分析、製片及交換結果等工作，不含人工框選、報告序列化與外層操作復原。基準另量確認到可操作的完整可見等待。 |

每格只讀時鐘、追加數字，平均與 nearest-rank P50／P95 在收尾才算。每項含次數與總時間；空分布的百分位是 null，不能當作零成本。處理格數、成功路徑格數、原計畫格數分開記錄。速度同時列每秒處理幾格與影片時間／分析時間的倍數；取消／失敗不拿來聲稱加速。分布目前保留已完成的 seek／影格擷取，取消中的未完成等待仍落在總時間；不要把部分輪當成完整分布。

目前下載報告為 schema 2，另列 `resultMs` 與 `totalFlowMs`；`totalAnalysisMs` 在製片前停止。製片取消／失敗仍回報部分數字，但不加入成功的同輸入比較，也不交換路徑或舊下載。原版基準收據維持 schema 1 與原始 hash，不用新欄位回填推測數值。

Window／Worker 使用 [Performance.timeOrigin 的跨情境換算](https://developer.mozilla.org/en-US/docs/Web/API/Performance/timeOrigin)，不拿兩邊 performance.now 直接相減。睡眠或不同時間精度造成換算落在本輪有效區間外時，啟動欄位留空；不以 Date.now 或推測延遲補成看似精確的數字。

## 可重現基準

在 Bun 1.4.4、已安裝 Chrome 與 FFmpeg／FFprobe 的環境：

```sh
bun run check
bun --no-env-file scripts/benchmark-follow.ts
```

工具先原子取得共用影音鎖，鎖忙即退出、不開瀏覽器或改別輪鎖。自行生成新的 60 秒 H.264／AAC 合成片：960×540、30fps，虛構成人圖片水平往返、660Hz 自製聲音；固定每 300 格關鍵影格並由 FFprobe 核對 0／10／20／30／40／50 秒。不是手機原片、Salsa 或遮擋品質驗收。

同一個乾淨隔離 Chrome context 先完成真正 SW 快取及重開，再用同一檔案、同裝置、同選框，分別分析老師／自己 10／30／60 秒，各跑兩次；每次仍建立新 Worker。資料已快取，但模型每輪重新初始化；不是冷網路下載基準。末尾關閉計時做兩輪同 10 秒對照。開關對照的順序與快取／排程波動仍可能影響結果，不能把小差異直接當成改善百分比。

本輪資料、來源 hash、靜態版本、裝置／瀏覽器版本、每輪真下載報告與失敗都留在新的 ignored output。完整關閉自己的 context／瀏覽器並核對已知 PID 全退出後，才核對 nonce 釋放自己的鎖。不能確認退出則保留鎖及收據。功能 CI 只驗欄位、樣本數、資料保全與取消，不把 CI 數字當 M4 Pro 或真機效能證據。

收尾分別嘗試關閉自己握有的瀏覽器與主機；CDP 稽核、close 或程序查核失敗，不會跳過其他資源的關閉。資源或 nonce 未確認時記錄失敗並保留鎖，原主流程錯誤仍保留。人物補邊仍在 Worker 等待內，detect 欄位只量等比補邊後的完整 detector.detect；下列舊基準繼續保留原來源，不移記新整合版。

## #192：一張照片的計算分批一起做

白話：每秒仍看八張照片，SIMD 讓電腦一次處理一排數字。像同樣洗八個盤子，工具做得快，沒有少洗盤子。不支援就用原本工具；若新工具開不起來，先完整關掉，再由新的助手用原工具試一次。兩次都失敗或你按取消，都保留上次影片。

技術：固定套件的 `FilesetResolver.isSimdSupported()` 選擇同源 `vision-simd.js/.wasm` 或 `vision-wasm.js/.wasm`，CPU、模型、補邊、門檻與取樣維持。SIMD 初始化失敗才把原 ImageBitmap 交還主執行緒，終止舊 Worker，再建相容 Worker；同一影格不重新擷取，沿用原三十秒偵測期限，不因回退重新計時。相容版只試一次，推論本身失敗維持原失敗保全。

碼表另外顯示實際 runtime、Worker 次數與回退次數。建構、啟動、程式載入與初始化累加已收到的重試成本；取消中未回覆的工作仍是部分數字。SIMD 能力探測留在 Worker 等待內，不混進模型初始化 API。成功重跑比較也要求 runtime 相同，不把相容輪與加速輪混成「暖機」。報告仍不含私人來源、影格、座標或裝置名稱。

兩套固定 runtime 都隨離線包與 SHA manifest 提供，代價是增加一份約14MB SIMD資源；保留完整離線回退，不改SW完整性驗證以省下載。基準先完成快取，不代表首次網路載入更快。官方能力 API 見 [FilesetResolver](https://developers.google.com/edge/api/mediapipe/js/tasks-vision.filesetresolver)，實作以鎖定的1.2.0套件為準。

本機對照可用 `bun --no-env-file scripts/benchmark-follow.ts <原基準的合成影片路徑> compare`，同一檔案 bytes、兩側10／30／60秒各兩輪，交錯 SIMD／相容順序。僅此合成診斷旁聽選框與偵測幾何，以原追蹤函式重播並核對真正製片的裁切；不擷取像素、不加入產品報告。再以 `bun --no-env-file scripts/compare-follow-benchmarks.ts <整合版run.json> <交錯對照run.json>` 比對同環境、格數、失聯、偵測框與裁切路徑。這些本機幾何收據留ignored output，不上傳。

先以互斥的定位總時間、影格擷取總時間、Worker 等待及其餘主執行緒時間排序；再拆 Worker 等待內的程式載入、模型初始化與推論。Worker 啟動可與其他步驟重疊，不另加一次。

- 初始化佔大宗：再做 Worker 重用實驗，保留取消、錯誤隔離及閒置釋放；量記憶體與同片重跑，不能只看一次快取命中。
- detect 佔大宗：再比較固定模型的 SIMD runtime 與相容 fallback，同時逐格核對追蹤品質；不先降 8 Hz。
- seek 佔大宗：再比較連續解碼與原定位流程，先核對時間戳、方向／旋轉、VFR、片尾與取消；requestVideoFrameCallback 不當作快速離線解碼器。
- 以上證據仍不足時，才另研究局部追蹤／週期重新偵測；不在本輪改演算法。

任何後續提升都要固定同素材、同裝置、同版本配置與快取條件做前後多輪，保留失敗、追蹤與匯出回歸，才報告改善；這份工具本身不代表已加速。
