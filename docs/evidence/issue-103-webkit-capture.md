# #103：錄影供聲的停止、逾時與重試

錄影前先準備示範聲音。如果這時按停止、畫面一直沒準備好，或錄到一半聲音停了，舊影片和筆記都應留著；中斷的新片能另存，再試一次也能完成。這份測試用合成影片與檔案相機檢查這些行為，不接觸真人影片或實體相機。

## 範圍與重跑

- 沿用原 `webkit-audio-branch.js` 完整建立既有比較與 VS；原檔、8 秒來源、原失敗／重試斷言均保留。
- 新案例接在原 67 條之後，完整入口變 68 條。相同既有合成相機、3 秒倒數、0.5×／來源 0–7.5 秒，實際錄影 15 秒；不縮短原素材或 2000ms 暖機期限。一般 UI 等待維持 15000ms，新長錄影與其 VS 匯出沿既有 capture-integrity 的 30000ms 操作期限，原 67 條全部不改。
- `bun run test:coverage:app` 跑完整入口；指定 `bun --no-env-file tests/app-coverage/run-app.ts webkit-audio-branch webkit-capture-branch` 跑兩條。先依既有入口準備合成素材，使用 `.bun-version` 固定版本並取得共用媒體鎖。
- 全部操作在 Chromium 明選 WebKit 程式分支；這不代表原生 Safari、真機、真人聽音或完整 G1–G7 已驗收。

## 斷言與取捨

1. 暖機時按公開停止鍵：暫留一次真正影格通知，停止後再送回同一 now／metadata；不開錄、不新增 chunks，移除影格訂閱與原計時器。遲到通知不能重新訂閱或寫資料。
2. 暖機逾時：沿原生 2000ms 期限，確認清楚提示及相同保全；不縮短時鐘或派發假事件。
3. 真正聲音中斷：原生錄影已產生 trusted 非空資料後，暫停同一 AudioContext。新段標 interrupted，原片與 chunks 完整指紋相同，不提前 finalize，舊播放器／下載仍可用。
4. 同頁同輸入重試：恢復原生音訊時鐘，重新開啟合成相機；新原片 ready、保存 bytes 與下載一致、chunks 清空，之後真正匯出 VS。

每輪都逐筆比對原筆記／take／recipe／VS 及原生媒體大小、MIME、SHA-256；聲音節點停止、斷線、buffer 釋放，相機 tracks ended。真正下載另由入口讀檔核對完整指紋。原片只有影像，VS 應有示範音訊，產品外播放分別記錄，不能用 VS 音軌替原片背書。

只旁聽原生 API，並明示兩個控制：延後真正影格通知、暫停真正音訊時鐘。排除直接呼叫內部 handler、假錄影事件、改原生片長、降低門檻與放寬 CSP。CSP 不允許 fetch(blob:)；測試改為保留原 Blob／原生 URL 對應，不更動產品安全政策或下載 bytes。
