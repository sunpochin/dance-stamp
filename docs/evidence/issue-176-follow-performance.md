# #176 人物分析耗時基準

## ELI5：先找最慢的一站

這次先量每一站花多久，沒有先換模型或減少分析格數。這組素材主要等在辨識人物，定位畫面排第二；每次重建模型的成本小得多。所以優先做同模型 SIMD 對照實驗，Worker 重用先不當主要解法。這是目前合成片的排序，不能代替私人舞蹈片的結果。

就像整理一疊照片，最久的是每張都要看清楚人在哪裡，拿下一張照片也花時間；重新打開工具箱卻很快。要讓整件事變快，先試縮短「每張照片的辨識」這一站，而不是先省開箱。SIMD 可想成一次算一排數字，仍須實測能省多少、會不會影響跟對人；本輪沒有套用它。

## 建議的下一個實驗

1. 優先比較同一固定模型的 SIMD WASM 與現行非 SIMD，保留 fallback，固定本片、M4 Pro、快取條件與 8Hz。固定套件已有兩類 runtime 資產，但本輪沒有切換；需另驗每格辨識／路徑、取消與真匯出，才決定採用。
2. 再用實際手機 codec／解析度／非零片段定位量測。只有 seek 比重明顯上升時，再做連續解碼候選；這支 10 秒 GOP 合成片的 seek 仍只有約 14%，不能推論所有手機片都相同。
3. Worker 重用作後續次要實驗。這組已快取素材的初始化約占 0.18%，本輪不支持把它列為主要等待原因；仍要量記憶體、首次推論與取消／錯誤隔離，不能只看少一次下載。

本次不包含尚未合併 PR #172 的單側成檔等待；該流程還有即時編碼成本，整合時必須將分析與成檔分開列。真人 Salsa、快速轉身／遮擋、私人原片、HEVC／HDR／VFR、原生 Safari、實體手機、冷網路及完整 G1–G7 均未由此基準驗證。沒有實作上述優化，也沒有拿此資料推論哇舞內部演算法或保證 Web 速度相同。

## 功能與失敗保全

`bun run check` 通過 662 個單元測試、typecheck、lint、建置及公開內容掃描。新增純統計與 Worker 邊界測試核對 nearest-rank、同輸入成功比較、十份上限、取消／失敗、時鐘失配留空、資料不外洩及關閉計時訊息相容。

同一應用來源的既有 person-follow、adjusted-side-preview、simplified-comparison 回歸通過，保留真模型、人物裁切／鏡像、可調框隔離、兩種 VS 成檔、停止與資料保全。新增 follow-performance 案例初輪錯用中央預設框，只覆蓋邊緣素材的半身，故真模型拒絕；修正為素材的完整身體選框，未改應用、模型、門檻或斷言。原失敗收據 app-GHHydi 保留，修正後獨立收據 app-rrRwOn 通過四輪真分析、計時開關、受控待回覆取消與 Worker 建構故障；兩側 3 秒各 25 格、原播放器位置與完整資料相同、Worker 每輪建立並終止。故障注入不當作自然 Safari 失敗或效能資料。

這些是選定功能回歸，不能寫成完整 App 矩陣通過；完整遠端 CI 另以 PR head 記錄。基準結束後再次核對量測三個應用模組的 SHA 與收據一致，測試修正未改變已量測版本。
