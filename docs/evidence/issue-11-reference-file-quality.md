# Safari 十份 VS 的示範側檔案品質

把已保存的影片拿出來，逐格看示範畫面上的時間碼，再核對每秒閃光與提示音，就能知道畫面有沒有停太久、聲音是否跟得上。這次十份影片的示範側最長停格為 122ms、最大聲畫差為 83ms，均在原門檻內。練習側沒有相同時間碼，所以兩邊人物是否同步仍未驗證。

這是 #11 的既有檔案分析，沒有再操作相機、瀏覽器或修改產品。原生十輪流程、完整保存與獨立重播來源見 [PR #159 的固定文件](https://github.com/sunpochin/dance-stamp/blob/8e401f1a61e576fab962033ade76607f42565e5a/docs/evidence/issue-11-safari-ten-cycle.md)。同來源在 [PR #143](https://github.com/sunpochin/dance-stamp/pull/143) 的第五輪失敗仍保留；新量測沒有定位其唯一根因。

## 固定來源與方法

- 影片受測產品：乾淨 `e6f0300aa9ce1c882ec1887f5f792ee8fe6b63de`／靜態 `4525b1293b89a584`，macOS 27.0.1／原生 Safari 27.0.1 一般視窗。十份都是原十輪實際保存的 VS，完整 SHA 與既有媒體收據一致，沒有重新編碼或補造影片。
- 文件基線為整合後的 main `0694f7326e6805db292ed2f9fff5aaa9dae4bc50`；不能把舊影片量測移記這個新版。原片與 VS 的 20 份完整解碼，以及十份 VS 原生自然重播到尾，維持各自既有紀錄。
- 沿 `scripts/analyze-media.py` v5 的示範側二進位解碼座標、灰階有效性檢查、原始 PTS、末格停留、合法交集 `[0,60)` 的閃光分組及對齊共同時間原點的完整 8kHz PCM。音軌延遲不歸零，不裁頭尾，不補／丟影格。
- 每份解出全片示範側時間碼；共 18,173 格，各檔影格數與先前完整 ffprobe 的原始計數相同。每份恰有 60 個片段內閃光及 60 個提示音，共 600 對，按順序配對，不用最近點隱藏整秒差。
- 原門檻引用 [RECORD_COMPARE](../RECORD_COMPARE.md#5-先做的可行性試驗與決策門檻)：每個閃光／聲音配對差 ≤100ms、來源起末覆蓋誤差 ≤100ms、非預期示範停格 ≤250ms。全片時間碼對輸出時鐘另沿 v5 的 250ms 品質容差；它不是兩側 G2 誤差。
- 原始 65 秒示範素材的 1,950 格碼逐一等於 0–1949，65 個聲音事件正確。分析輸入的 500ms 停格與音軌移後 1 秒兩個負例均被原門檻拒絕；原始媒體未修改。
