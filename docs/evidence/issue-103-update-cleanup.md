# #103：更新失敗後仍能操作與重試

## 怎麼用、為什麼有效

使用方式不變：新版準備好後，先保存工作，再按「立即更新」。如果訊息送不出去，或等十秒還沒完成，頁面應恢復原來的可操作狀態、顯示失敗原因，讓使用者在同一頁再試。只有候選版本真正接管才重新載入。

這次只替既有保護補上檢查，沒有發現必須修改的產品缺口。除了看按鈕恢復，也確認訊息通道、事件監聽與等待計時器有收好，避免表面能再按，背後卻留下前一次等待。

## 固定來源與範圍

基底為同步 main `1fbbf5ba38633723a34e3695ebc8ee7fd5885fcb`，沿用 Bun 1.4.4。十二份產品 JS、來源綁定計數器、分母、忽略規則與原瀏覽器案例不改。`web/offline.js` SHA256 為 `84e0032d931798ca571966d94fa6103f2d6c67f271bfb0ae7fe19e780ab0b59a`；不帶入尚未合併 PR 的產品或數字。

沿原 `startOffline` 入口與既有能力介面測試，只控制候選 worker 的失敗邊界；EventTarget、MessageChannel 與十秒計時器仍由真正執行環境排程。三個新案例覆蓋：

- 傳送同步拋錯後恢復操作，以及頁面原先已為 inert 時仍保留原狀態。
- 候選不回覆時等原十秒期限；無關 controllerchange 與尚在 activating 的 statechange 不可冒充完成。
- 兩種失敗均核對沒有重載、舊 controller 保留、兩個 port 關閉、兩種 listener 移除、原計時器清除，再走同頁真實事件重試到一次重載；重試本身也清除資源。

測試自己的等待預算涵蓋產品原十秒期限，沒有縮短、替換或延長產品計時器。初版新增測試曾被測試框架預設五秒上限中止（15 pass／1 fail）；原失敗保留，修正為十五秒測試預算及明確等可觀察結果，未改產品期限或弱化斷言。
