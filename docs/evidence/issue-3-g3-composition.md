## 根因與整合

前輪 [基線證據](issue-3-media-feasibility.md) 的原 take 最長相同畫面約 46ms，合成右側卻停住約 264–268ms；減少 playbackRate 寫入未穩定改善。

本輪固定同一段合成原片，觀察解碼呈現及播放器位置：合成時兩個來源 video 位於 viewport 上方約 869px，時鐘仍正常前進。只加入持續的 requestVideoFrameCallback 訂閱、保留原本的速率調整，就讓輸出右側最長停格降到 68.100ms、三點配方誤差約 1ms 內。這是本機 Chrome 的控制條件比較，不宣稱所有瀏覽器內部實作相同。

先前試驗版本 `43bd33208136c5e2` 完成九組矩陣與五輪長錄影。期間 main 合併 PR #35，已在共用合成為兩側持續訂閱實際影格、畫好 canvas 後明確 requestFrame。故撤下本輪重複實作，直接整合最新 main；舊試驗數據保留本機，不計入下方最終通過數量。

最終版本沿用 rAF 共同時鐘、偏差校正及看門狗；每側最多一個影格回呼，結束／取消會撤銷。不支援手動 canvas 擷取時保留 30fps 自動路徑，沒有影格 API 的裝置仍須另驗 G3。未提高門檻、略過開頭、裁去失敗影格或引入轉碼套件。

### 中途版本的音訊配對邊界校正

中途 `cbc5dee` 的第六組（0.75×／60 秒）成檔後，舊分析器以 46 次畫面閃光／45 次提示音停止。逐幀確認額外閃光出現在輸出 PTS 60.002333 秒，來源編號 1350，即來源第 45 秒、恰好是配方 B。音訊解碼到 60.010750 秒，最後有效提示音是來源第 44 秒，符合片段 `[0,45)`；沒有缺少片段內的提示音。

分析器 v2 只將合法交集內的閃光用於聲音配對，片段外末格另列 `boundaryFlashPts`；所有影格仍參與完整解碼、首末配方誤差及 G3，未裁片或放寬門檻。先前七段（短片及六組矩陣）全部另存 v2 報告重新分析通過；原錯誤 JSON／報告保留，沒有覆寫。產品靜態內容未變，故從尚未執行的第七組接續，不借用不同產品版本。

v2 六項工具自查通過預期：對齊與末格邊界為正例；畫面錯開 200ms、聲音延遲 200／1200ms、真正中段缺音均拒絕。另重分析原停格案例仍拒絕 266.400ms。缺音測片採區塊邊界前後皆靜音，避免 FFmpeg volume 啟用時間留下短脈衝而沒真的造出缺音；初次造片與失敗結果同樣保留。

### PR #41 完整性與本輪保存審查

兩項 P2 均成立。v4 曾誤放行「60 秒配方只有 15 秒檔案」，以及時長 60 秒但兩側都把同一段 15 秒重播四次的內容。v5 獨立核對合法交集的預期長度、解碼視訊／影音長度、來源起末時間碼覆蓋與原 take 長度；來源與輸出邊界容差 100ms，沿用同步門檻並涵蓋慢速來源影格量化。相機原片另獨立核對 runner 規劃長度的既有 500ms 容差。兩個真實成檔負例均拒絕，不再以同步或能解碼代替完整性。

全部 24 組另存 v5 報告覆核通過，解碼視訊長度誤差最大 46.466ms、來源邊界誤差最大 44.444ms、全片內容時鐘誤差最大 108.333ms，48 份內容指紋不變；再從每份原片及 VS 的實際 Blob 指紋回查 take→recipe→export，24 對均一一正確。v4 報告保留，不覆寫。所有來源時間碼還須跟隨輸出時鐘，偏移不超過既有 G3 的 250ms，避免首末正確卻在中途重播。
