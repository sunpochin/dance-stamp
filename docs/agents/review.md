# 審查、失敗排查與交接

本文件補充 [工作流程](workflow.md)，不新增合併、發布、自動回覆或結案授權。

## 審查與排查

1. 固定這次的 base／head，閱讀完整 diff 與相依呼叫端；工作樹有未提交內容時明說，不能把它當成乾淨 commit 的證據。
2. 收到人工或工具意見，先判斷是否正確、相關及可重現。檢查影片／筆記保全、資源釋放、取消、時間映射與資料交換邊界；不要只看嚴重度標籤。
3. 以最小案例區分產品、測試、環境或能力限制。保留原失敗與版本；受控注入要明說，不當作自然平台故障。
4. 同一方向連續兩次有意義修正仍失敗，重新檢查假設、呼叫順序與根因，必要時交由使用者或獨立審查者判斷；不反覆改 mock 或弱化斷言。
5. 同意後做最小修正，驗證原問題與相鄰失敗路徑；不同意時保留理由與證據。未修好、未驗證或仍有爭議的意見不能宣稱解決。

圖譜或搜尋工具可協助定位相依；索引必須對應目前來源與版本。文件、workflow、JSON、授權與工具不支援的格式仍直接看 diff；沒有圖譜結果不代表沒有風險。工具不可用時用 repo 內的搜尋、程式與測試，不自行安裝或借用另一個產品的執行環境。

## 交付證據

PR 讓沒看過對話的人也能判斷結果，至少記錄：

- 使用者遇到什麼、修改後如何改善，以及對應 issue。
- 受測 commit、工作樹是否有額外修改、實際執行的檢查與結果。
- 與該 head 對應的 CI、審查者及 reviewed commit；新提交與新意見到達後重新核對，不能沿用舊綠燈。
- 未驗證、失敗、受控注入及裝置限制。影片、音訊與備份證據按 [驗收範本](acceptance-template.md)，公開內容只放匿名摘要與合成素材。
- 未完成的延伸工作與下一步；同一成果沿用原 issue，獨立範圍另建關聯 issue，不把整份規格複製到多處。

自動化檢查、獨立審查、裝置驗收、合併與發布是不同結果。沒有 findings 不能當作已完成獨立審查，工具顯示可合併也不代表已獲合併授權。
規格與決策留在 repo；issue／PR 連回正式文件並保存進度，不能只把知識留在聊天或個人 memory。
