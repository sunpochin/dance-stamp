# 自主練習回合 Practice Sessions

[#259](https://github.com/sunpochin/dance-stamp/issues/259) 保留為 P1 提案，尚未排入實作。原先的「每天練哪段」縮小為回顧時的一個選擇：下次想再練哪段？

## 已確認方向：為下一場舞會準備一個動作（2026-11-04）

白話：先想一個下次舞會想用的課堂動作，在住處或選定的練習地點把它練到有機會用出來，再到舞會繼續熟悉。使用者已同意先以這個方向探索「怎樣才願意開始練」，並補充首先需要一個此刻願意花時間練的理由，幫自己開始動起來。提醒帶出自選動作與本人認同的理由；「不用一直看示範，也能跟音樂跳完所選片段」由本人判斷，速度與試用方法再細化。下方原有觀察／跟跳／回顧流程保留為候選，尚未證明能促成這個結果。

### 兩個時機需要不同幫助

使用者進一步提出兩種需求：還在滑手機、尚未進工具時，需要有人提醒停下來想起練習；進工具後，需要手把手帶著完成準備。這裡把兩者稱為「練習提醒」與「開練引導」，定義見[詞彙表](../GLOSSARY.md)。

| 時機 | 舞者需要的幫助 | 尚待確認 |
| --- | --- | --- |
| 尚未進工具 | 本人選下一次開始準備的時間；第一次先用手機現有提醒工具手動設定時間與練習理由，收到後再開 Dance Stamp。沒空可延後、改期或這次不練，未回應不追加催促。 | 實際試用所用工具、通知送達與操作；不能假定工具知道本人正在用哪個 App。 |
| 已進工具 | 先選在住處練、準備外出練或已到練習地點，再依已確認清單逐步準備。按「準備好了」才前進，可略過已完成或不需要的步驟，中途離開保留進度；準備好後開所選片段，自選先看示範或直接跟跳。 | 常用地點怎樣選，以及返回時如何確認與繼續。 |

白話示意是「想起下次舞會想用的一招 → 開工具 → 選今天在哪裡練 → 做眼前這一步 → 開所選片段，先看或跟跳」。三種情境的準備清單已確認；已換好衣服、已在場地或不需要換裝的人可略過不需要的步驟。閱讀提醒、完成準備與實際跟跳須分別辨認，不把提醒點擊或穿好鞋當成已練。

### 已確認的提醒與引導方式（2026-11-04）

白話：先由舞者自己約下一次「開始準備」的日期和時間，練完再約之後的時間。提醒帶出想練的動作和本人的理由，例如「週五想要練出這個 shine」；沒空就延後、改期或這次不練，沒回應不再催。開工具後先選在住處、準備外出或已到練習地點，再像有人陪著準備，一次只說眼前一件事；按「準備好了」才往下，做過或不需要的事情可以跳過，中途離開保留進度。

| Q3 | 所選時間是開始準備，每次先約下一次，練完再決定之後的時間。 |
| Q4 | 可延後、改期或這次不練；未回應不追加催促。 |
| Q5 | 提醒帶出自選動作與本人認同的理由；「週五想要練出這個 shine」是使用者提供的文案示例。 |

已確認的 Q11 準備清單：

技術決策：Q9 是舞者自評，不新增 AI 評分，也未指定速度、次數或保證舞會表現；Q10 允許直接跟跳，不把原候選的三輪觀察當成必要前置。Q12 只選定第一次試用的人工提醒途徑，未指定供應商或建立真實排程；網站內排程／Push 仍未實作。示例的「週五」是練習理由中的目標描述，不當成每週五重複提醒；Q7 不延伸為已接受所有中斷恢復細節。這些界線用來避免把接受試用方式當成已驗證有效，或把準備進度當成真的練過。

### 帳號與保留進度的界線

白話：選在哪裡練、記住準備到哪一步，不必先註冊 Dance Stamp 帳號。使用者已選第一版先在同一台裝置收提醒與保留進度，像把準備清單放在手邊；換另一台裝置接著準備不列為這一版的完成條件。

技術：沿用核心免登入與資料預設不外傳的規則，先將準備進度設計為同一份本機資料的延續，不新增必要的身分登入。第一次提醒採本人操作的現有手機工具，送達仍須實測，不能把免登入或保存進度當成網站已能在關頁後準時送達。既有 [#209 雲端候選](CLOUD_SYNC_SHARING.md) 以本人明確連接的供應商帳號保存選定資料，不要求另一套 Dance Stamp 會員；新提醒與準備進度尚未定義或納入該封套，不能宣稱既有 Google 連接已涵蓋。本輪不新增帳號、同步或服務。

### 工具外提醒的可行性（技術查證，2026-11-04）

現行產品程式未串接系統通知或其他 App 的使用紀錄。觸發來源已確認為本人選定的下一次開始準備時間，Q12 已選第一次試用先由本人在現有手機工具手動安排提醒；具體工具與送達仍待試用。Web Push 留作後續可能方案，本輪未建立排程或新增服務。

- [MDN Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API) 說明通知由作業系統顯示，需使用者授權；手機應使用 Service Worker 的持續通知。這只說明能在其他 App 前顯示通知，不表示網站得知對方正在滑手機。
- [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API) 說明標準 Push API 可接收伺服器傳來的訊息，包含網站不在前景或未載入時；送達來源、排程與訂閱處理都還要設計及驗證。
- [WebKit 的 iOS／iPadOS 說明](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) 列出加入主畫面及由使用者操作申請權限的要求。這是文件查證，非本產品手機通知已驗收；也不因此把 iOS 原生 App 列為前置。
- 人工提醒有現成能力：[Apple 提醒事項指南](https://support.apple.com/en-au/guide/iphone/iphec7a1de82/27/ios/27) 說明可加筆記、連結與日期時間，部分功能依其帳號類型而異；[Google Tasks 建立說明](https://support.google.com/tasks/answer/7675838?co=GENIE.Platform%3DAndroid&hl=en) 與[通知設定](https://support.google.com/tasks/answer/13486720?co=GENIE.Platform%3DAndroid&hl=en) 說明日期時間及通知權限，亦列出系統可能延遲通知。這些支持 Q12 已接受的人工試用途徑，不代表網站可自動寫入，也不代表供應商完全免帳號、已整合或準時送達；使用者尚未選定具體工具。

原候選下方的「沒有推播」描述先前產品範圍。首次試用的人工提醒不需要新增網站推播；通知是否收到及是否促成開練仍須各自觀察，原候選不能代替這個新需求的驗收。

### 匿名訪談線索與適用範圍

- 一位受訪舞者描述，曾因近期舞會有實際用招及與舞友互動的機會，而在家先練；疲累時，知道練習有價值仍不保證會開始。

- 課堂動作在舞會用得出來、獲得舞友回應，是這次訪談出現的動機線索。它們尚未經前瞻試用，也不能推論其他學生有相同動機。

## 原有回合流程候選

舞者本來只看一次課後示範。現在想跟跳時，點一下就回到剛才卡住的地方，看老師的腳步、跟著跳，再決定要不要多練一回。老師不用出題、開帳號或批改。有些舞者期待被老師看見進步；是否分享由舞者自己決定，本版不發送回報、影片或通知。

## 一回怎麼練

> **今天把這 8 拍練熟 · Shine 第 3 段**
>
> 00:18–00:26 · A–B 循環 · 0.75× · 預計五分鐘
>
> **1/3　觀察**　先看老師示範三次，留意腳步方向與重心。
>
> **已觀察，開始跟跳**

這是畫面文案示例，五分鐘是舞者給自己的時間。「8 拍」是舞者自己選的名稱。無拍點也能用原片秒數圈選，系統不從秒數推算舞步。

| 階段 | 舞者操作與回應 |
| --- | --- |
| 進入 | 從正常桌面首頁選一支有權使用的示範片，手動設 A/B 或選既有區間標記。單點標記需補終點。在已保存片段、原片可用時，一次點「開始練」就從 A 播放，無須事先建計畫、選第二支影片或登入。 |
| 1 · 觀察 | 慢速、鏡像與 A–B 沿用現有練習播放。例中完整播三輪後停回 A，等舞者按「開始跟跳」；可提早切換或再看。暫停、跳轉或播放失敗不算一輪，不推定人已跟跳。 |
| 2 · 跟跳 | 同段反覆播放，舞者可調速、鏡像、暫停或結束。錄自己是明確點選的選項，符合既有錄影條件才依 #9 啟動。拒絕授權、中斷或片段不合條件時仍可繼續跟跳與回顧。 |
| 3 · 回顧 | 舞者確認「我有跟跳」，可選「還不熟／比上次順／這段先放下」，也可略過自評。有錄影可回放自己的錄影；沒錄影也能保存這一回。只看示範、提早離開或按兩次儲存都不增加跟跳回合數。 |

**Practice Plan 的角色。** 回顧時可按「下次再練這段」。下次開啟先顯示手選片段，否則建議最近一次自評「還不熟」的片段，並說明理由。用每段最新自評，已改選「先放下」或「比上次順」就不繼續以舊自評推薦。沒有候選就讓舞者選段。可忽略或換段，缺片時提示重連。第一版沒有日曆、每日待辦、連續打卡、XP、排行榜、AI 評分或推播。

## 同一段的第一次與第五次

- 每個已存片段有穩定 ID、來源影片、段名與 A/B 快照，每個回合連回該片段；Marker 僅是選段來源。修改或刪除 Marker 要提示並保留原片段，改練不同 A/B 時另存片段，避免兩段的進步混在一起。A/B 必須是原片整數毫秒且滿足 `0 ≤ A < B ≤ 影片長度`。
- 同段的歷史依時間列出舞者自報有跟跳的回合、當時速度、自評及可選的 take ID。可直接選例如「第 1 回」與「第 5 回」，依序回放兩次自己的錄影並看到各自的感受。某回沒錄、錄影已刪或原片待重連時照樣顯示該回，指出缺哪一份，不拿別回頂替。
- 首版驗收的是從自己的歷史直接取回兩份原錄影。老師與自己的比較沿用既有配方；把兩次自拍重新對時、並排或合成另一支 VS 等需求，另依 [錄影比較規格](RECORD_COMPARE.md) 評估。拿掉錄影連結不刪回合，刪回合也不連帶刪媒體或既有比較。

## 接現有播放、錄影與保存

2026-11-03 對照 `main` 的 `e55bd04`。以下是現有程式的限制與提案要補的路徑。

- 首頁 `data-comparison-only` 會隱藏練習區。回合要有自己的可見入口，取得既有循環的播放能力，同時保護比較共用的 A/B 欄位。遇比較、錄影、匯出或未存草稿先提示完成或取消；停止、離頁和播放拒絕要保留原工作，已開啟的相機依既有流程釋放。[首頁](../web/index.html)／[播放器](../web/main.js)
- 示範中的八秒以 0.75× 播一次約 10.7 秒。用現有 `captureDuration` 核對，這組輸入會被錄影下限拒絕；同段在 0.5× 得到 16 秒，符合時長條件。畫面應解釋原因，提供繼續不錄或由舞者主動調整的選擇。不替舞者改速、拉長片段或把幾次循環拼成一個 take。這次只核對時間函式，未操作相機。[錄影時長驗證](../web/timeline.js)
- #17 現有歷史按 Marker 與 take 的區間交集推算，無法代表一次沒有錄影的練習。新回合保存穩定 ID、片段快照、回報時間、自評及可選的 take 連結；確定有跟跳才記一次，重試與雙擊沿用同一回合 ID。回合、自評及下次所選片段透過 IndexedDB 既有 revision 驗證一併提交。[歷史與備份](../web/library.js)／[交易](../web/storage.js)
- 完整本機 JSON 帶回合、片段、自評、下次選擇及來源關聯，原片和自拍另存。現行 v2 只重建已知欄位；新版完整備份需能讀 v1/v2 並為舊資料建立空回合，舊程式遇新版應拒絕。匯入衝突保留副本並改寫相關 ID，重匯不重複計數。既有筆記分享、Google 選定練習快照和成品連結均排除回合、自評與下次選擇。[資料格式](DATA_FORMAT.md)／[雲端快照](../web/cloud-snapshot.js)
- 缺片可讀歷史、可換段。重新連結要預覽並人工確認，候選短於 B 時禁止啟動該區間。取消或解碼錯誤保留舊連結與媒體。移除瀏覽器副本保留歷史；明確刪除整份筆記須列出受影響回合並確認。quota、分頁競寫或壞資料不能覆寫舊資料；交易結果未確認時依既有救援流程重新讀回。核心免登入、免付費 API，原片、自拍與筆記預設只在裝置。

## 原產品實驗：會不會多練兩次？（新方向的驗收待確認）

以下是原提案尚未執行的七天觀察方法。舞會準備方向的成功條件仍待訪談確認，不能把「兩個跟跳回合」直接當成「已準備好在舞會使用」，也不能把舞會上的反覆用招計作已完成的居家回合。

找一位平常只看一次 recap、看完沒有再跟跳的自願舞者。試用前由本人確認這個習慣；用一段獲准使用的課堂影片觀察七天。唯一判準是：第一次看過後，是否有 **至少兩個由本人自願開始、實際跟跳並自己確認的獨立回合**。不設每日次數或最低時長。

同一回的循環、播放次數、按鈕點擊、重載或錄影數量都不計成額外回合。本人可用簡短本機紀錄核對，無須錄影作證，也不請老師催練。若少於兩回，保留實際次數與卡住的地方，先決定修正或停止，不擴充排程功能。只對外記匿名結果；這項單人試用尚未執行，不能據此認定所有舞者的動機或產品成效。
